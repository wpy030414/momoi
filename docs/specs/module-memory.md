# Spec — 跨会话用户记忆（User-Agent Memory）

## 概述

跨会话记忆让 Agent 在**不同会话中记得同一个用户**：用户说过的重要事实（称呼、身份、稳定偏好、长期约定、重要日期）被持久化后，会在之后每次对话开始时自动回到 Agent 的提示词里，不随会话清空或新建而丢失。

整体是**不对称设计**：**读**由系统提示词自动注入（零成本，模型不必"想起来要用"），**写**由 `save_memory` 工具显式调用（有成本、有边界，避免污染），**管**交给用户在记忆管理界面自查自清。

**边界说明**：

- 记忆按 `(user_id, agent_id)` 二元组隔离——每个 Agent 各自"认识"用户，互不串味。
- **中立 Agent 没有记忆**（其记忆无归属意义）：注入与工具暴露均跳过，`/api/memories` 对其返回 403。
- **QQ 群聊完全不启用记忆**（多真人场景，隐私与归属错位）：不注入、不暴露工具、执行层拒绝写入，见 D-M06。
- 同一对 `(user, agent)` 最多只注入**最近 30 条**（更早的仍在库中、仍可在管理界面看到，只是不进提示词）。
- **不做向量检索 / RAG**（与 `AGENTS.md` 非目标一致）：注入是全量的最近 N 条纯文本列表。

## 设计决策

### D-M01：记忆归属为什么是 (user_id, agent_id) 二元组

**问题**：记忆应该属于用户、属于 Agent，还是属于会话？

**决策**：属于 `(用户, Agent)` 对。

**依据**：

- 属于会话 = 不能跨会话，等于没有记忆
- 属于用户 = 所有 Agent 共享一份记忆，人格会串味（群聊里两个 Agent 会说出同一套"认识你"的话）
- 属于 `(用户, Agent)` 既跨会话、又保持每个 Agent 的人格独立
- Agent 被删除时**不做级联清理**（无外键），残留行作为"孤儿"继续显示在管理界面供用户清理——宁可多留，也不静默丢数据

### D-M02：为什么读自动、写显式

**问题**：记忆的读写都应该由模型决定吗？

**决策**：读自动注入，写靠工具。

**依据**：

- 读如果也靠工具，模型必须"先想起自己有记忆"才会去查——这一步在长人设、角色扮演场景下极易失败（本设计的直接动因）
- 写如果也自动化（如每轮后台提取），会产生大量低质条目，且用户无从审阅；写必须是一个可被提示词约束、可被用户看见的动作
- 推论：读块与写规则必须**分别注入**——写规则即使在该 Agent 尚无任何记忆时也要注入（否则永远写不进第一条）

### D-M03：为什么 Agent 端只有 save_memory，没有 update / delete / list

**决策**：Agent 只能写，修改与遗忘只由用户（或管理员）执行。

**依据**：

- 记忆是"Agent 对用户的认知"，让 Agent 自行改写历史记忆，等于让它自说自话地篡改对用户的印象
- 用户侧已有完整 CRUD（记忆管理界面），修正成本很低
- 工具数量直接影响模型的工具选择质量：只暴露一个写工具，命中率最高

**代价**：用户说「刚才记错了，其实是 X」时，Agent 无法修正，只能再存一条相互矛盾的记忆，需用户到界面里清理。记录在案（见「未来扩展」）。

### D-M04：为什么只注入 30 条、时间正序、纯文本

**决策**：取最新的 30 条，恢复为时间正序（旧→新）后作为编号列表注入。

**依据**：

- 30 条 ≈ 提示词成本的量级上限，且覆盖绝大多数 Agent 的实际记忆量
- 时间正序符合"认识一个人"的阅读方式（从头读起）
- 纯文本无 schema 开销，模型可直接引用
- 超限时**静默丢弃最旧**——这是已知取舍；写规则里明写"只取最近 30 条"来抑制无节制写入

### D-M05：为什么记忆加载下沉进 runPiAgentLoop

**问题**：记忆应该在调用方加载（网页 / 群聊 / 微信 / QQ 各自加载），还是在 `runPiAgentLoop` 内部统一加载？

**决策**：下沉到 `runPiAgentLoop`，`RunPiAgentLoopOptions` 不再有 `userMemories`。

**依据**：

- **对称性**：`save_memory` 工具在所有渠道无条件可用，读也必须全渠道一致。此前微信 / QQ 链路没传 `userMemories`，形成"写而不读"——工具描述承诺的"下次会话自动注入"在那两个渠道是假的
- **一致性**：调用方传的 `agentId` 与工具实际执行时用的 `resolvedAgentId` 可能不同（Agent 被删除时 `pi-adapter` 会回退到第一个非中立 Agent）。在调用方加载会出现"读 A 的记忆、写进 B 的记忆"
- **单一事实来源**：`memoryEnabled` 判定（非中立 Agent）只写一处，新增渠道自动获得记忆能力

**代价**：`pi-adapter` 承担了一次 DB 读取（原本它已 import `lib/config` 并负责解析 `resolvedAgent`，依赖方向未变）；无限模式下从"整场复用一份"变为"每轮重读"——语义上更好（第 N 轮保存的记忆第 N+1 轮就能看到）。

### D-M06：为什么 QQ 群聊完全不启用记忆

**问题**：QQ 群聊里要不要用跨会话记忆？

**决策**：**完全不用**——不注入 `## 用户记忆`、不注入写规则块、不暴露 `save_memory`、工具执行层独立拒绝写入。

**依据**：

- **归属错位**：QQ 群聊的 `userId` 是**机器人绑定者**（Momoi 账户所有者），而群里的发言者可能是任何群成员（`authorOpenid` 是另一个人）。记忆的语义是"关于当前用户"，在群里这句话没有主语。
- **隐私**：注入 = 把绑定者的私人记忆投放到多人群里。群友随口一问，Agent 可能主动说出主人从未打算公开的事——消息所有群成员都看得到，**无法撤回**。
- **污染且不可逆**：写入 = 群成员的事被记成绑定者的记忆，挤占 30 条注入上限，且用户事后很难分辨哪些条目来自群里。
- **两害相权**：QQ 私聊（一对一）与微信（一对一）**照常启用**记忆；只有"一个 Agent 面对多个真人"的群聊场景被排除。

**实现**：

- `runPiAgentLoop` 中 `memoryEnabled = 非中立 Agent && !isQqGroup`——注入与工具暴露**同源**，不会出现"能写不能读"或反之
- `ToolContext.memoryDisabled` 让工具执行层**独立兜底**，不依赖"工具没被暴露"这一层假设
- QQ 群聊规则块新增一条声明：不要向群成员许诺「我会记住」——做不到的承诺比沉默更伤信任

### D-M07：为什么积极性靠提示词规则而不是配置开关

**问题**：如何控制 Agent 保存记忆的积极性？

**决策**：不提供 per-agent 开关；积极性由系统提示词的"必须调用 / 主动调用 / 不要调用"三档边界 + 工具描述共同决定。

**依据**：

- 开关只能开/关整个记忆能力，无法表达"用户明确要求时必存、琐事不存"这种粒度
- 记忆的收益完全来自"该记的记、不该记的不记"，这正是提示词擅长的
- 排除类需求（中立 Agent、身份未知）用**身份判定**而非配置项

## 数据模型

表 `user_agent_memories`：

| 列 | 类型 | 说明 |
|---|---|---|
| `id` | TEXT PK | UUID |
| `user_id` | TEXT NOT NULL | Momoi 用户名 |
| `agent_id` | TEXT NOT NULL | Agent ID（可为已被删除的 Agent → 孤儿行） |
| `content` | TEXT NOT NULL | 记忆正文，上限 4000 字符（三处常量同步：`memory-tool.ts` / `routes/memories.ts` / `MemoryManager.tsx`） |
| `source` | TEXT NOT NULL DEFAULT 'agent' | `'agent'` = `save_memory` 写入，`'user'` = 界面手动添加；只作展示区分 |
| `created_at` | INTEGER NOT NULL | Unix 秒 |

索引：`idx_user_agent_memories(user_id, agent_id)`（注入查询的覆盖路径）。

**编辑语义**：`updateUserAgentMemory` **有意不更新 `created_at`**——保持注入列表的时间线稳定，改一个字不该让这条记忆跳到最新。

## 工具与注入

### 工具（save_memory）

#### save_memory

**参数**：

- `content` (string, required): 记忆正文，写为脱离当前对话也能读懂的陈述句（如「用户希望被称呼为『鹿鹿』」）

**行为流程**：

1. `content` 去空白；空 → `Memory content cannot be empty.`（error）
2. 长度 > 4000 → `Memory content too long (...)`（error）
3. `ctx.agentId` 为空 → `Cannot save memory: agent identity unknown.`（error）
4. `saveUserAgentMemory(userId, agentId, content, 'agent')`
5. 返回摘要 `Memory saved for all future sessions: "<前 200 字预览>"`

**错误与边界情况**：

| 场景 | 行为 |
|---|---|
| 内容为空 / 超长 | 返回 error，不写库 |
| Agent 身份未知 | 返回 error，不写库 |
| 中立 Agent | 工具**不暴露**（`createToolAdapter` 按 `toolCtx.agentId` 过滤），而非执行时报错 |
| 上下文禁用记忆（QQ 群聊） | 工具**不暴露**（按 `toolCtx.memoryDisabled` 过滤）；即使被调用也返回 `Cannot save memory: cross-session memory is disabled in this conversation.`（执行层兜底，见 D-M06） |
| 同一条事实重复保存 | 不拦截（无去重）——靠工具描述里的「返回成功即已持久化，不需要重复保存」抑制 |

**设计意图**：

- **不做去重**：服务端判重需要语义比较（成本高、易误判），交给模型自觉 + 用户界面清理
- **工具描述即触发规则**：三档清单（必须调用 / 主动调用 / 不要调用）写进 description，与系统提示词规则块互为冗余——触发词（「记住」「记一下」「别忘了」「永远记住」「以后都要」）逐字出现在两处，因为这是"用户说了什么"到"必须调用"的直接映射
- **返回摘要带正向反馈**：工具返回值同样是提示词的一部分，`Memory saved for all future sessions` 明确告知"已持久化"，抑制同轮反复保存

### 系统提示词注入

`buildSystemPrompt()` 注入两个**互不相同**的块（见 D-M02）：

| 块 | 位置 | 注入条件 | 作用 |
|---|---|---|---|
| `## 用户记忆` | 语言彩蛋之后、**人设之前** | `memoryEnabled` 且 `userMemories` 非空 | 背景数据：这是你此前保存的、你认识他的依据 |
| `## 跨会话记忆` | 人设之后、**行为规则区首位**（`/no_think` 之后、群聊规则之前） | `memoryEnabled` | 行为规范：何时必须调用 `save_memory` |

`memoryEnabled` 的定义（唯一判定，注入与工具暴露同源）：`非中立 Agent && !QQ 群聊`，即 `!!resolvedAgentId && resolvedAgentId !== NEUTRAL_AGENT_ID && !isQqGroup`（见 D-M05、D-M06）。

**位置理由**：人设之前被模型当作"叙述性背景"，人设之后被当作"操作规范"。写记忆是行为，必须落在行为区；放在人设之后还能获得 recency 优势——本设计要解决的核心失败模式正是"人设太强、模型留在角色里，把「你要永远记住」当成剧情台词回应"。

**框架理由**：写规则块以「记忆让你在不同的会话里依然是同一个你」开口，与人设**同向**而非对抗——记忆是为人设服务的能力，不是外部系统指令。结尾一句「调用工具是你自己的事，不必在回复里解释」用于消除"调用工具会打断角色扮演"的顾虑。

**提示词段落顺序**（`buildSystemPrompt`）：

```
语言彩蛋 → ## 用户记忆 → [Agent 人设] → /no_think → ## 跨会话记忆
→ 群聊规则 → QQ群规则 → 本轮发言角色 → 无限演算模式 → 环境信息 → 可用技能
```

**写规则块三档边界**（与工具描述一致，改一处必须改另一处）：

- **必须调用**：用户说「记住」「记一下」「别忘了」「永远记住」「以后都要…」→ 同一轮内调用，先存再回应；「只在回复里说我记住了 = 没记住」
- **主动调用**：称呼与自称、身份与职业、稳定的偏好与习惯、长期约定与计划、重要日期
- **不要调用**：一次性的、临时的、剧情内的琐事

### 加载链路

| 渠道 | 注入 | 说明 |
|---|---|---|
| 网页单聊 | ✅ | `userId` + `resolvedAgentId` |
| 网页群聊 | ✅ | 每个 Agent 各读自己的（`(user, agent)` 隔离，互不串味） |
| 无限模式 | ✅ | 每轮重新读取（第 N 轮存下的记忆，第 N+1 轮即可见） |
| 微信 / QQ 私聊 | ✅ | 下沉后自动获得（修复前为"写而不读"） |
| QQ 群聊 | ❌ | **完全禁用**（D-M06）：不注入、不暴露 `save_memory`、执行层拒绝写入。`userId` 是机器人绑定者而非群内发言者，注入等于把绑定者的私人记忆投放给全体群成员；群聊规则块另有一条「不启用跨会话记忆」声明，禁止许诺「我会记住」 |
| 中立 Agent | ❌ | `memoryEnabled = false`：不注入、不暴露工具 |

## API 端点

均挂载在 `/api/memories`（`userAuthMiddleware`；单机模式下直通 `userId='admin'`）：

| 方法 | 路径 | 行为 | 错误 |
|---|---|---|---|
| GET | `/` | 当前用户**全部**记忆（跨 Agent，新→旧），含孤儿行 | — |
| POST | `/` | 手动新增一条（`agent_id` + `content`）→ `source='user'` | 空/超长 400；中立 Agent 403；Agent 不存在 404 |
| PUT | `/:id` | 改单条内容（限本人） | 空/超长 400；不存在 404 |
| DELETE | `/:id` | 删单条（限本人） | 不存在 404 |
| DELETE | `/agent/:agentId` | 清空某 Agent 下的全部记忆（限本人） | — |
| POST | `/api/admin/users/:username/forget-memories` | 管理员遗忘某用户的全部记忆 | 遗忘自己 403；用户不存在 404 |

## 前端集成

- **入口**：侧边栏设置菜单 →「记忆」（`menu.memory`）→ `handleMemory()` 打开视图；hash 路由 `#/memories/{agentId}`，带路由守卫（非管理员无关；Agent 被删则回退到有记忆的第一个 Agent 或列表首项）
- **`MemorySidebar`**：按 Agent 导航（含记忆条数徽标）+「已删除的 Agent」孤儿分组
- **`MemoryManager`**：条目列表 + 新增/编辑/删除/按 Agent 清空；客户端分页 50 条/页；4000 字前端校验与计数
- **`source` 徽标**：`Agent 记下`（secondary）/ `手动添加`（primary）——用户据此分辨 AI 写入的条目并清理
- **已知限制**：记忆变更不广播 SSE 通知，其他设备需刷新后才可见

## 验收标准

### 提示词触发验收

1. ✅ Agent 提示词中使用「记住」「记一下」「别忘了」「永远记住」「以后都要」等说法时，**同一轮内**调用 `save_memory`——实测判据：`messages.trace` 含 `save_memory` 调用记录
2. ✅ 仅口头回复「我记住了」而无工具调用，判为**失败**
3. ✅ 用户未开口但透露明显长期事实（称呼、身份、稳定偏好）时主动调用
4. ✅ 一次性安排、剧情琐事不触发调用
5. ✅ 无任何记忆的 Agent 也收到 `## 跨会话记忆` 规则块（否则第一条永远写不进去）
6. ✅ 中立 Agent 既不收到记忆块，工具列表里也没有 `save_memory`

### 注入验收

7. ✅ 有记忆时注入 `## 用户记忆` 块，位置在人设之前、编号列表按时间正序
8. ✅ 注入上限 30 条，超出时丢弃最旧（不是报错）
9. ✅ 读块与写规则块位置分离：读块在人设前、写规则块在人设后的行为规则区

### 加载链路验收

10. ✅ 网页单聊 / 群聊 / 无限模式 / 微信 / QQ 私聊均注入记忆（下沉后调用方无需感知）
11. ✅ 工具写入的 `agent_id` 与注入时使用的 Agent **严格一致**（Agent 被删除回退时也不出现"读 A 写 B"）
12. ✅ 群聊中两个 Agent 各持自己的记忆，互不出现在对方提示词里
13. ✅ QQ 群聊不注入记忆（提示词中无「## 用户记忆」与「## 跨会话记忆」）、工具列表中不含 `save_memory`
14. ✅ QQ 群聊中即使强行调用 `save_memory` 也返回拒绝错误且不写库（`ctx.memoryDisabled` 兜底）
